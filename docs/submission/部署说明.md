# 智演 JobEvolution 部署说明

作品编号：XH-202621
作品名称：多源异构数据驱动岗位和能力图谱构建与动态演化分析研究

本文写给评审方和复现方：拿到源码后如何把系统在一台普通 Linux / macOS 服务器上跑起来，如何填充图谱数据，如何跑通三项准确率评测与单元测试，以及如何验证部署成功。全部步骤都已在本仓库的干净容器环境下复现通过（Docker 29.4 + Compose v5.1.2）。

## 1. 部署形态

单机 Docker Compose，五个服务一个命令启动，不再拆微服务：

| 服务 | 镜像 | 作用 | 地址 |
| --- | --- | --- | --- |
| `web` | `apps/web/Dockerfile` | Next.js 前端 | http://localhost:3000 |
| `api` | `apps/api/Dockerfile` | FastAPI 接口 | http://localhost:8000 |
| `pipeline` | `apps/api/Dockerfile` | 每日采集 + 抽取 + 入谱 + 发布 | 无 HTTP 地址 |
| `neo4j` | `neo4j:5-community` | 岗位能力图谱 | http://localhost:7474 / bolt://localhost:7687 |
| `redis` | `redis:7-alpine` | 会话、事件流、任务状态 | localhost:6379 |
| `sessions` | `redis:7-alpine` | 简历上传会话（与业务 Redis 隔离） | 无对外端口 |

`api` 与 `pipeline` 共用同一份 `apps/api` 基础镜像。应用数据落在 `data/official-only/jd/`（3,595 条官方 JD 原文，随仓库分发）、`data/snapshot/`（图谱快照）与 `data/eval-official-only/`（评测金标与两岗提交物），由 Compose 以 `./data:/app/data` 挂载进容器，不写入镜像。克隆仓库即拿到全部数据文件，不需要另行下载。

## 2. 环境要求

| 项 | 要求 |
| --- | --- |
| Docker Engine | 支持 `docker compose`（Compose v2，即 `docker compose` 子命令） |
| 磁盘 | 镜像约 4.5 GB（web 镜像 1.07 GB），数据卷 2–3 GB，建议预留 15 GB |
| 内存 | 建议 ≥ 8 GB。Neo4j 堆上限 1 G + 页缓存 512 M，按需在 compose 里调 |
| GPU | 不需要 |
| 网络 | 能访问招聘门户（腾讯、字节、智谱、MiniMax 等 ATS）与所选模型服务端点 |
| Docker Desktop / 宿主机 | macOS 用 Docker Desktop；Linux 用 Docker Engine |

仅跑前端开发服务器或单元测试时，还需要宿主机 Node.js 22 与 Python 3.12（详见第 7、8 节）。

## 3. 一键启动

### 3.1 复制环境变量并填写

```bash
cp .env.example .env
```

`LLM_PROVIDER` 决定用哪家模型供应商，三选一，仅需填对应那一行的 Key：

```dotenv
LLM_PROVIDER=deepseek
DEEPSEEK_API_KEY=你的密钥

# 或
LLM_PROVIDER=bai
BAI_API_KEY=你的密钥

# 或
LLM_PROVIDER=tuzi
TUZI_API_KEY=你的密钥
```

`ADMIN_PASSWORD` 是管理后台口令，务必改成强口令，不要用示例值 `change-me`。

### 3.2 启动全部服务

```bash
docker compose up -d --build
```

首次启动会构建 `api`、`web` 镜像并启动全部容器。`pipeline` 以单容器循环运行：`while true; do python -m app.collectors --daily; sleep 86400; done`，即每天自动采集、抽取并发布一次图谱。

### 3.3 检查健康状态

```bash
docker compose ps
```

六个容器（含 `sessions`）启动，`web` / `api` / `neo4j` / `redis` 应显示 `(healthy)`。

```bash
curl http://localhost:8000/meta
```

返回 JSON，其中 `graph_release`、`ops` 字段应存在。

## 4. 图谱数据：两种填充方式

系统启动后图谱初始为「空壳」——只有代码写死的四个 `Domain`（ai / data / system / iot）和五个 `SkillCategory`，`Job`、`Skill`、要求边、演化事件全部来自管线或快照。有两种方式把业务数据填进去。

### 4.1 方式 A：每日管线自动填充（默认，适合长期运行）

`pipeline` 容器每天触发 `app.collectors --daily`：采集官方门户 JD → 抽取技能点 → 审核闸门 → 写入 Neo4j → 公开校准 → 发布图谱版本。该方式需要：

- 一个可用的 `LLM_PROVIDER` + 对应 Key（抽取与审核都调用模型）；
- 服务器能访问 ATS 招聘门户。

手动跑一次（宿主机，需先建虚拟环境，见第 8 节）：

```bash
PYTHONPATH=apps/api .venv/bin/python -m app.collectors --daily
```

### 4.2 方式 B：从图谱快照恢复（适合演示 / 提交 / 冷启动）

仓库自带一份经过校对的图谱快照 `data/snapshot/reviewed.json`（与 `release-2026-09-05.json` 字节一致，SHA-256 `30b08a59…64dc6`，约 87 MB），可在空卷上重建整张图谱：12 个岗位、1646 项技能、3593 条证据、3905 个演化事件、223 个要求版本、9 个岗位定义与声明、3757 个审核提案、3435 个审核决定，以及公开指针指向的那一份已发布图谱版本。

做法：在 `.env` 里追加一行（`.env.example` 末尾已有注释掉的同名行），再启动。API 启动时检测到图为空（仅 `Domain` / `SkillCategory`）会自动导入，图非空时跳过，不会覆盖已有数据。图谱里每条证据只存指向 `data/official-only/jd/` 的路径，原文随仓库一起分发，因此证据抽屉与诊断发布校验在恢复后即可读到 JD 正文。

```dotenv
SNAPSHOT_PATH=/app/data/snapshot/reviewed.json
```

```bash
docker compose up -d --build
docker compose logs -f api        # 首次导入约 1–2 分钟，看到 Uvicorn running 即完成
curl http://localhost:8000/meta   # graph_release.id 应为 release-5a60dff52dd80ac49c151be2
```

`docker-compose.yml` 默认给 `neo4j` 1G 堆，已验证该配置可完整导入本快照。若自行导出了未加 `--slim` 的全量快照（200 MB 以上）再导入，可能报 `MemoryPoolOutOfMemoryError`，此时把 `NEO4J_server_memory_heap_max__size` 临时调到 2G 即可。

该快照已在本机临时空 Neo4j 卷上验证：恢复后 `/meta` 正确解析公开 release、`/jobs` 返回 9 个公开岗位、`/discover` 列出候选 3 / 新兴 2 / 成型 7、`/graph/jobs/{id}` 返回要求边与季度变化。

### 4.3 重新导出快照（图谱更新后）

管线运行一段时间后若要刷新随仓库分发的快照，从产品库重新导出：

```bash
SNAPSHOT_PATH="" NEO4J_URI=bolt://localhost:7687 NEO4J_USER=neo4j \
NEO4J_PASSWORD=jobevolution DATA_DIR=data/official-only \
PYTHONPATH=apps/api .venv/bin/python -m app.graph_snapshot export data/snapshot/reviewed.json --slim
```

`--slim` 只保留公开指针指向的那一份 `GraphRelease` 的预计算快照，其余历史 release 保留 id / period / metadata 但清空 `snapshot` 字段；不加该参数会把全部历史 release 的预计算快照一起导出，文件会膨胀到 200 MB 以上。导出前先确认 `/meta` 的 `graph_release` 是想要分发的版本。

## 5. 关键配置项（.env）

以 `.env.example` 为准，常用项：

| 变量 | 作用 | 默认 |
| --- | --- | --- |
| `LLM_PROVIDER` | 模型供应商：`deepseek` / `bai` / `tuzi` | `deepseek` |
| `DEEPSEEK_API_KEY` / `BAI_API_KEY` / `TUZI_API_KEY` | 对应供应商 Key | 空 |
| `EMBED_API_KEY` | 可选：硅基流动 `BAAI/bge-m3` 嵌入（技能对齐、消解、聚类） | 空 |
| `ADMIN_PASSWORD` | 管理后台口令 | `change-me` |
| `NEXT_PUBLIC_API_URL` | 前端请求 API 的地址；构建期注入 web 镜像 | `http://localhost:8000` |
| `CORS_ORIGINS` | 允许访问 API 的来源，逗号分隔 | `http://localhost:3000,http://localhost:3001` |
| `NEO4J_USER` / `NEO4J_PASSWORD` | Neo4j 登录信息 | `neo4j` / `jobevolution` |
| `ALIGN_THRESHOLD` | 技能对齐余弦阈值 | `0.70` |
| `COLLECT_KNOWN_PAGES` | 每个关键词连续多少页无正文变化即停 | `2` |
| `COLLECT_FULL_SCAN` | 设为 1 全量扫描（补历史） | `0` |
| `EXTRACT_WORKERS` / `PORTAL_WORKERS` / `EVAL_WORKERS` | 抽取 / 采集 / 评测并发 | `8` / `4` / 按供应商 |
| `NEXT_PUBLIC_SHOW_ADMIN_PASSWORD` | 设为 1 时管理页明文显示口令 | `0` |

## 6. 访问入口

| 用途 | 地址 | 说明 |
| --- | --- | --- |
| 前端 | http://localhost:3000 | 首页总览、图谱工作台、五步诊断、市场演化、管理后台 |
| API 健康检查 | http://localhost:8000/meta | `graph_release`、`ops`、`stale` |
| 管理后台 | http://localhost:3000/admin | 用 `ADMIN_PASSWORD` 登录 |
| Neo4j 控制台 | http://localhost:7474 | 图谱可视化；Bolt 端口 7687 |
| 公开接口 | `/jobs`、`/discover`、`/graph/jobs/{id}`、`/diagnose`、`/feed`、`/pulse`、`/events/stream`(SSE) | `api` 服务 |

生产环境建议把 `web` 与 `api` 放在同一 HTTPS 反向代理之后同源暴露，并仅在 `CORS_ORIGINS` 列出可信来源；`ADMIN_PASSWORD` 不与 Cookie 同存，缺省情况下 Cookie 走 `httponly`，`ADMIN_COOKIE_SECURE=1` 可强制 Secure 标记。

## 7. 单元测试与三项评测

### 7.1 单元测试（覆盖率 ≥ 60%）

测试固定连独立的测试 Neo4j 库（`bolt://localhost:17687`），永不写产品图。先起测试库：

```bash
docker compose --profile test up -d neo4j-test
```

在宿主机（需 Python 3.12 虚拟环境）：

```bash
PYTHONPATH=apps/api TEST_NEO4J_URI=bolt://localhost:17687 .venv/bin/python -m pytest --cov -q
```

本仓库洁净复现结果：**179 passed, 1 skipped，覆盖率 69.67% ≥ 60%**，门禁 `fail_under = 60`（见 `.coveragerc`）。前端检查：`cd apps/web && npm run typecheck && npm run build`。

### 7.2 三项 F1 评测（赛题硬指标 ≥ 0.90）

金标与提交物在 `data/eval-official-only/`（100 条 JD、100 份简历、100 对匹配）。在宿主机分别跑：

```bash
EVAL_DIR=data/eval-official-only PYTHONPATH=apps/api .venv/bin/python -m app.eval jd
EVAL_DIR=data/eval-official-only PYTHONPATH=apps/api .venv/bin/python -m app.eval resume
EVAL_DIR=data/eval-official-only PYTHONPATH=apps/api .venv/bin/python -m app.eval match
EVAL_DIR=data/eval-official-only PYTHONPATH=apps/api .venv/bin/python -m app.eval report
```

`report` 汇总写入 `data/eval-official-only/out/summary.md`。任一 F1 < 0.90 时对应子命令退出码为 1。`summary.md` 必须来自未 mock 的本地跑；CI 跑 mock 版三项 + `pytest --cov -q`。

## 8. 宿主机开发环境（可选）

只跑前端开发或后端测试、管线命令时，不建议整栈 Compose 内的 `api`/`pipeline`/`web`，而是让 Docker 负责基础件、宿主机跑应用：

```bash
docker compose up -d neo4j redis sessions
python3.12 -m venv .venv && .venv/bin/pip install -e 'apps/api[dev]'   # 后端
cd apps/web && npm install && npm run dev                              # 前端（:3000）
```

## 9. 图谱版本发布（运维）

公开读接口走「已发布图谱快照」而非实时图。修改了 `graph.py` 里被快照预计算的读函数后，重建 API 容器还不够，需重新发布版本并让指针切换到新 release：

```bash
curl -X POST http://localhost:8000/admin/releases \
  -H "X-Admin-Password: $ADMIN_PASSWORD" \
  -H "Content-Type: application/json" \
  -d '{"period": "2026-09-05", "metadata": {"reason": "..."}}'
```

注意 `period` 必须是 `YYYY-MM-DD` 日期字符串（页面按 Date 解析）；写 `2026Q3` 这类非日期串会导致前端 `new Date(period).toISOString()` 抛出 `RangeError` 而白屏。回滚：`POST /admin/releases/{release_id}/rollback`。release 一经发布不可变，按 id 在进程内缓存解析结果（约 48 MB），指针切换自动失效缓存。

## 10. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| `/meta` 返回 `stale: true` | 管线最近一次未成功或有待清理的陈旧发布；检视 `ops` 字段，或手动重跑 `--daily` 再发布 |
| 空卷启动后图谱无岗位 | 默认按方式 A 需管线 + LLM Key 才能填充；演示/提交请改为方式 B（`.env` 设 `SNAPSHOT_PATH=/app/data/snapshot/reviewed.json`） |
| `snapshot relationship has invalid type or missing endpoint` | 快照文件与当前导入器不匹配（多为旧版导出）；按 4.3 从产品库重新导出 |
| 前端首页白屏（时报错 `toISOString` / `RangeError`） | `period` 被写成非日期串（如 `2026Q3`）；重新发布时用 `YYYY-MM-DD` |
| `Neo4j ... 连不上` | 先起 Neo4j；测试场景先 `docker compose --profile test up -d neo4j-test` |
| 改了 `.tsx` 但前端没变 | Compose 的 `web` 镜像不挂载源码；`docker compose up -d --build web` |
| 改了 API 代码但接口没变 | `api` 容器不挂载源码、且公开读走已发布快照；`docker compose up -d --build api` 后再重新发布 |
